## 실제 구독 백엔드 검증

gpt-5.6-luna에서 Responses/Chat × 텍스트/함수 호출 × 스트리밍/비스트리밍
8가지 조합 모두 통과했습니다. 사용자 로그인으로 저장된 OAuth 자격 증명을 사용했습니다.

실제 백엔드가 output_item.done에는 답변을 넣지만 마지막 response.completed의
output은 빈 배열로 보내는 동작을 확인했습니다. 비스트리밍은 완료된 출력 항목을
순서대로 수집하도록 수정했고, Chat 스트리밍의 함수 호출 완료 사유도 보완했습니다.
같은 동작을 모의 백엔드 회귀 테스트에 반영했습니다. 수정본을 재설치했습니다.

동일 모델·본문·캐시 키로 직접/프록시 호출을 순서대로 비교했습니다.

| 순서 | 경로 | 입력 토큰 | 캐시 토큰 | 출력 토큰 |
| --- | --- | ---: | ---: | ---: |
| 1 | 직접 | 4574 | 0 | 5 |
| 2 | 프록시 | 4574 | 3840 | 5 |
| 3 | 직접 | 4574 | 3840 | 5 |
| 4 | 프록시 | 4574 | 3840 | 5 |

이 입력에서는 프록시 경로에서도 같은 캐시 적중값을 관측했습니다.
모든 요청의 캐시 적중을 보장한다는 뜻은 아닙니다.

서버 실행 후 재현: `uv run scripts/verify_live.py`,
`uv run scripts/verify_cache.py`. 실제 구독 사용량을 소비합니다.
캐시 검증은 저장된 OAuth 자격 증명을 로컬에서 읽어 직접 호출에도 사용하고,
토큰을 출력하지 않습니다.

## 아직 확인하지 않은 항목

- 실제 OAuth 브라우저 상호작용 자동 검증 및 실제 토큰 갱신/401 재시도.
- 실제 백엔드에서 취소 후 연산 종료 여부 (모의 HTTP 백엔드 연결 종료는 확인).
- 공개 HTTPS 설치 주소, GitHub 릴리스 실행, macOS/ARM 실행 검증.
- 다중 serve 프로세스 사이의 인증 파일 갱신 조정은 지원 범위 밖입니다.

## 실제 캐시 비교 절차

1. `codexy login`으로 전용 인증 파일을 만들고 `codexy serve`를 실행합니다.
2. 같은 모델, 충분히 긴 동일 프롬프트 접두부, 같은 `prompt_cache_key`로
   Responses 요청을 반복합니다. 요청의 원문·계정 토큰을 로그에 남기지 않습니다.
3. 직접 호출에도 프록시가 정규화한 동일 본문과 같은 session-id를 사용합니다.
   OAuth 토큰을 채팅·셸 기록에 복사하지 않는 로컬 검증 도구를 사용합니다.
4. 각 실행의 input_tokens와 cached_tokens 및 실행 순서를 기록합니다.
   먼저 실행한 경로가 캐시를 가열할 수 있으므로 순서를 바꿔 반복합니다.
5. 적중이 없다고 프록시 오류로 단정하지 않습니다. 백엔드 정책·접두부 길이와
   유지 기간을 고려하고, 실제 관측값을 그대로 기록합니다.
